HTTPS and cert-manager
=====================
Flux installs pinned cert-manager chart v1.21.2, then retrieves the ACME
email using ESO, registers the issuer, issues the certificate, and updates
the central Gateway. No manual secret copying or certificate installation.

Dependency order
----------------
- cert-manager: controller and CRDs.
- acme-email: waits for the GCP SecretStore, then retrieves email-account
  into Secret acme-email in flux-system with key ACME_EMAIL.
- cert-issuers: waits for cert-manager and acme-email; Flux substitutes the
  required Secret value into the ClusterIssuer's email field.
- gateway-certificate: waits for the issuer and Envoy namespace/controller,
  then issues grafana.iso.michaelalinks.com's certificate into grafana-tls
  in envoy-gateway-system.
- gateway-config: waits for the certificate before adding HTTPS on port 443.

Google Workload Identity is used throughout. The cert-manager Kubernetes
service account maps to the same GCP account as ESO and ExternalDNS. Cloud
DNS DNS-01 challenges are limited to the grafana-assessment managed zone
for iso.michaelalinks.com. There are no GCP JSON keys or GitHub credentials.

Email and key ownership
-----------------------
The email-account secret and its enabled version are managed in the GCP
console. The ignored Terraform grants secret-level access to the shared
GCP service account. ESO trims surrounding whitespace from the email.
The actual email is never committed; it is present in the live Kubernetes
Secret and ClusterIssuer, since cert-manager requires a literal email field.
Changes to the ESO-produced Secret trigger issuer reconciliation via the
Flux watch label. A missing Secret blocks issuer reconciliation.
cert-manager generates the ACME account key in cert-manager and the TLS
private key in envoy-gateway-system. Private keys are never stored in Git.
The certificate uses ECDSA P-256 and rotates its key during reissuance.
Renewal is automatic. ExternalDNS manages A/TXT ownership records;
cert-manager manages temporary _acme-challenge TXT records independently.
The generated keys may change on a full cluster recreation. Avoid repeated
rapid full rebuilds because Let's Encrypt production rate limits apply.

Central Gateway routing
-----------------------
Gateway public remains in envoy-gateway-system. It has HTTP and HTTPS
listeners, with TLS termination using Secret grafana-tls. The HTTP listener
has an HTTPRoute redirecting grafana.iso.michaelalinks.com to HTTPS. This
route also supplies the hostname to ExternalDNS, which creates the A record.
Future Grafana's HTTPRoute lives in its application namespace and attaches
to Gateway public, sectionName https. Grafana's Service remains internal.
HTTPS initially returns 404 until the application's HTTPS backend route is
installed; this is expected, and does not indicate a certificate failure.

Safe verification (no secret values)
------------------------------------
kubectl -n cert-manager get helmrelease cert-manager
kubectl -n flux-system get externalsecret acme-email
kubectl get clusterissuer letsencrypt-gcp -o jsonpath='{.status.conditions[*].type}{" "}{.status.conditions[*].status}{"\n"}'
kubectl -n envoy-gateway-system get certificate grafana
kubectl -n envoy-gateway-system get gateway public
curl -I http://grafana.iso.michaelalinks.com
curl -I https://grafana.iso.michaelalinks.com
Do not use kubectl get secrets -o yaml or output the substituted issuer
manifest when recording submission evidence.
